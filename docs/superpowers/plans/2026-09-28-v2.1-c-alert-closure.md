# TraceMind V2.1-C "告警闭环" 实施计划(v1,待审查)

> 本切片对应方案 §V2.1 条目 9-10 与"完成标准"(自动调查 E2E),即 V2.1-A/B 之外剩余部分:
> **resolved 复核、历史基线、自动调查 E2E**。计划只描述设计与验证方案,**不含编码**;
> 审查通过后再按 TDD(先红后绿)实施,并单独提交。
>
> 本轮服务保持关闭:不做 live 验收、不做真实库迁移;`012` 迁移脚本先写并做本机
> 迁移门禁测试,真库增量应用等审查通过、服务可开时再执行。

**Goal:** 告警自动创建的 Incident 能完成一次**可信**的完整调查——基线来自告警
`startsAt` 之前的历史窗口(不是故障态实时值),`resolved` 到达时做复核而不是直接宣告
恢复,调查终止且全部告警非 FIRING 后才关闭 episode。

**Architecture:** 在现有"Webhook 快速持久化 → 租约 Dispatcher → 快照驱动图执行"链路上,
把**基线采集从"Incident 创建时"移到"Run 启动前"**(Dispatcher 内、图启动前一次性冻结),
并新增两个确定性控制点:图内的 `resolved_recheck` 节点(动态 resolved 信号)与写路径前的
`preflight`(proposal 不用旧快照执行)。

---

## Global Constraints

- **不伪造健康基线**:历史窗口不满足最小样本数/健康阈值 → 记 `BASELINE_INSUFFICIENT`,
  Verifier 走显式 SLO 或 `INCONCLUSIVE`,**不得**把故障态当前值当基线、**不得**默认"通过"。
- **webhook 仍然只做快速持久化**:不同步采集基线、不同步跑图、不读业务库。
- **冻结契约不回退**:Run 启动后(存在 checkpoint)不得再改写 RunContextSnapshot 的
  任何基线字段;恢复只读快照 + 一次性写入的冻结列。
- **resolved 不等于恢复**:不得直接宣告恢复、不得删除或取消 Run、不得清 `open_group_key`。
- **写路径唯一**:修复执行仍只有 `fix_service.execute_fix` 一条路径;Preflight 不通过
  → 零写操作 + 转人工。
- 不改已发布 migration(010/011);新增 `012` 追加式。
- 三状态分离不变:`incident.alert_status` / `incident.lifecycle_status` / `agent_run.status`。

## 三、启动前基线冻结(核心设计,需裁决 D1)

### 3.1 为什么必须移到 Run 启动前

- webhook 不能采集基线(方案条目 6:不同步采集 5 秒基线);
- Incident 创建时的实时值在告警场景下就是故障态(方案条目 10 明确禁止);
- E3 需要"调查窗口起点之前的累计计数快照"才能算增量,而累计快照只能从业务库实时读。

因此:两类基线统一在 **Dispatcher 领取成功后、图启动之前**一次性采集并冻结。

### 3.2 流程(新增 Dispatcher 阶段)

```
claim_queued_run(owner)            -- 已实现:READY/过期 CLAIMED → CLAIMED
  ↓
capture_run_baselines(run)         -- 新增:一次性、幂等、失败不阻断调度
  ├─ digest 基线:业务库 performance_schema 累计快照(capture_digest_baseline)
  ├─ 健康基线:Prometheus 历史窗口 [startsAt-10m, startsAt-1m] 的 p95/qps/error_rate
  ├─ 写 agent_run.incident_digest_baseline + baseline_capture_status
  ├─ 写 RunContextSnapshot.baseline_ref / healthy_baseline_ref / baseline_quality / baseline_window
  └─ 写 incident.baseline_window_*/baseline_metrics_json/baseline_quality/auto_run_started_at
  ↓
mark_dispatched(run_id, owner)     -- 已实现:CAS(owner + 租约未过期)
  ↓
start_investigation(...)           -- 已实现:快照驱动
```

- 采集与 `mark_dispatched` 在**同一事务**提交:失败则整体回滚,Run 留在 CLAIMED,
  由租约过期回收重试(不会出现"已 DISPATCHED 但基线没写"的中间态)。
- 图启动后再也不碰这些字段;`recover_pending_runs`/`resume_investigation` 只读快照。
- 冻结契约的落地方式:新增 `run_context.freeze_baselines(run, ...)`,**仅允许**在
  `status in (queued, CLAIMED)` 且该 Run 无 checkpoint 且 `baseline_capture_status IS NULL`
  时调用(否则抛 `RunContextInvalid`);调用后 `baseline_capture_status` 非空,天然幂等。
  这一条替代"创建时冻结",语义等价(首个图节点执行前冻结),但不违反"webhook 快速返回"。

### 3.3 历史健康窗口校验(不伪造基线)

```python
# app/services/health_baseline_service.py(重写采集来源)
BASELINE_WINDOW_BEFORE_START = 10m     # startsAt-10m
BASELINE_WINDOW_END_BEFORE_START = 1m  # startsAt-1m
BASELINE_MIN_SAMPLES = 30              # 窗口内最少样本数(配置项)
BASELINE_MAX_P95_MS = 100              # 健康阈值(= demo 告警规则阈值,配置项)
```

- 窗口内样本数 < `BASELINE_MIN_SAMPLES` → `BASELINE_INSUFFICIENT`;
- 窗口 p95 > `BASELINE_MAX_P95_MS`(故障在告警触发前已发生,窗口被污染)→ `BASELINE_INSUFFICIENT`;
- 两种情况都**照常落 `baseline_window_*` 与 `baseline_quality`**,只是不写 `baseline_metrics_json`
  的健康值(不伪造),E1 走显式 SLO 分支(§六)。
- Prometheus 侧新增能力(仍只跑固定模板,**不接受 LLM 生成 PromQL**):
  `PrometheusMetricsClient.query_at(template_id, labels, window_seconds, at_time)`
  (instant query 带显式 `time`)+ `sample_count(template_id, labels, start, end)`
  (`/api/v1/query_range` 或 `count_over_time` 固定模板)。模板继续注册在
  `promql_templates.TEMPLATES`,新增 `*_RANGE_V1` 两个模板。

### 3.4 手动创建 Incident 的路径

`incidents.py` 保留 `capture_health_baseline`(Java 实时值),但改名为
`capture_current_health_snapshot` 并**明确标注为"当前快照,不是健康基线"**,
写 `incident.healthy_metrics_baseline` 供人工调试;手动 Run 的 digest 基线仍在
`create_run(baseline=...)` 传入。是否把手动路径也切到历史窗口,见 D1-b。

## 四、resolved 复核(图内确定性节点)

### 4.1 图变更

```
collect_evidence → resolved_recheck → diagnose     (新节点, 条件边)
                        └─ self_recovered → report (新增终态)
```

`resolved_recheck(state)` 逻辑(全部确定性,LLM 不参与):

1. 读 `incident.alert_status`(**动态信号**,不参与冻结上下文,与 RunContextSnapshot 无关);
2. 非 `RESOLVED` → 直接返回 `{"resolved_recheck": {"status": "not_resolved"}}`,零额外开销;
3. `RESOLVED` 且该 Run 已有 `FixExecution`(已执行写动作)→ 不宣告恢复,返回
   `{"resolved_recheck": {"status": "write_already_executed"}}` → 继续 `diagnose`;
4. `RESOLVED` 且尚未执行写动作:
   - 复用本轮刚采集的 E1 证据(其 `latestSampleAt` 在 `metrics_max_age_seconds` 内即视为高时效);
     否则发一次 `get_service_metrics`(新窗口)重采;
   - 判定:`p95 <= baseline*1.2`(有健康基线)**或** `p95 <= 显式 SLO`(无健康基线,见 §六)
     → `status = SELF_RECOVERED`;
   - 否则 → `{"resolved_recheck": {"status": "still_degraded"}}` → 继续 `diagnose`(不宣告恢复);
5. 决策与依据写 Replay 步骤(`ALERT_RESOLVED_RECHECK`,含 alert_status、样本时间、
   使用的阈值与来源:baseline / SLO),保证可回放、可审计。

### 4.2 新增终态 `SELF_RECOVERED`

- 加入 `run_repo.TERMINAL_STATUSES`(终态清 `active_run_key`/租约);
- `_finalize_run` 的 outcome 映射增加 `SELF_RECOVERED → "self_recovered"`(replay 步进);
- `run.status` / `incident.status` 允许该值;前端状态文案与 SSE 一并处理(见 D5);
- 语义边界:`SELF_RECOVERED` **只表示"告警已 resolved 且指标已恢复,且未执行任何写动作"**,
  不表示根因已确认;根因未知时报告写"未确认根因(告警自愈)"。

### 4.3 审批等待期内的 resolved

图停在 `human_approval`(interrupt)时不会被 `resolved_recheck` 覆盖 → 由 §五 Preflight
在写路径前兜底复核;两者互补,缺一不可。

## 五、Preflight 重新验证(写路径前的最后闸门)

`app/services/fix_service.py` 在 `FIX_ACTIONS` 校验之后、真正执行 DDL 之前,新增
`preflight(incident_id, proposal, approval, agent_run_id)`:

| 检查 | 不通过时的行为 |
|---|---|
| proposal 生成时间 vs `incident.last_seen_at`/`closed_at`:proposal 是否来自 resolved 之前的旧快照 | 拒绝 |
| 目标索引当前是否已存在(可能被前一次执行/人工创建) | 已存在 → 走既有 `no_op`(不变) |
| 前置条件是否仍成立:重新读 `EXPLAIN`(仍为 `access_type=ALL`)+ 当前 p95 仍高于阈值 | 已恢复 → 拒绝执行 |
| `incident.alert_status == RESOLVED` 且指标已恢复 | 拒绝执行(转人工) |

- 拒绝时:零写操作,`FixExecution` 不落 `succeeded`,`incident.status = needs_human`,
  `termination_reason = PREFLIGHT_STALE_PROPOSAL`(或 `PREFLIGHT_ALREADY_RECOVERED`);
- 拒绝结果写 Replay(`PREFLIGHT_REJECTED`,含每项检查的实测值),供坐席判断;
- 幂等键不变(`{incident_id}:{proposal_id}:{parameters_hash}`),Preflight 不改变幂等语义。

## 六、Verifier:显式 SLO / INCONCLUSIVE(关闭 fail-open)

`recovery_service.py` 现状:`_p95_recovered` 在 baseline 缺失时 `return True`(默认通过)。

改为:

```python
SLO_P95_MS = 100   # 显式 SLO(与 demo 告警规则阈值同源,配置项,非"默认通过")
```

| 情形 | 判定 |
|---|---|
| 有健康基线 | `p95_after <= baseline*1.2`(不变) |
| 无健康基线(`baseline_quality=BASELINE_INSUFFICIENT`) | 用**显式 SLO**:`p95_after <= SLO_P95_MS`;并在 `RecoveryCheck.result` 记录"判定来源=SLO" |
| 无基线且 SLO 也无法判定(p95 缺失/采集失败) | `status = INCONCLUSIVE` |

`RecoveryCheck.status` 为 `String(16)`,`INCONCLUSIVE`(12)可容纳;`nodes.verify_recovery_node`
增加分支:`INCONCLUSIVE` → `needs_human` + `termination_reason = recovery_inconclusive`
(与 `recovery_failed` 区分,既不宣告恢复也不宣告失败)。

**回归风险(需专项验证)**:现有 SCN-001/002 E2E 脚本依赖"修复后 recovered";
基线缺失时原来"默认通过"的路径会变成 SLO 判定。SCN-001 修复后 P95 应远低于 100ms,
判定结果不变;但必须在专项测试中逐条确认,不得靠放宽阈值掩盖。

## 七、episode 关闭与 `open_group_key` 释放

新增 `app/services/incident_lifecycle.py`:

```python
def maybe_close_incident(session, incident_id) -> bool:
    """同一事务内满足全部条件才关闭 episode:
    ① alert_status == 'RESOLVED';
    ② 关联 AlertInstance 全部非 FIRING(复用 _firing_instances_remaining == 0);
    ③ 该 Incident 无活动 Run(agent_run.active_run_key IS NULL,即全部 Run 已终态);
    ④ lifecycle_status 仍为 OPEN。
    → lifecycle_status='CLOSED', open_group_key=NULL, closed_at=now。
    """
```

调用点(**必须同事务**):

1. `run_repo.update_run_status` 进入终态后(同一 Session/事务内)调用 —— 覆盖
   "Run 终止 + 告警已 resolved" 的组合;
2. 网关 resolved 路径(aggregation 事务内)调用 —— 覆盖"Run 早已终态、之后才 resolved"。

不变量:

- resolved 到达但 Run 未终态 → **不清** `open_group_key`、**不关** lifecycle(方案条目 9/数据表注);
- 关闭后再次 FIRING → `open_group_key` 为 NULL → 走 `_insert_incident` 创建**新 episode**
  (新 Incident + 新 queued Run),这正是 011 唯一键设计的用途;
- 关闭与 Run 终态同事务 → 不会出现"已关闭但仍有活动 Run"。

## 八、SSE 事件(需裁决 D4)

`incident_event` 表以 `incident_id` 为键(sequence 自增),因此**只能在 Incident 已知后**发事件。
按此约束落地:

| 方案事件 | 落点 | 说明 |
|---|---|---|
| `alert.received` | 聚合事务内,已解析出 Incident 后 | 无法在"尚未知道 Incident"时发;偏离字面定义,见 D4 |
| `incident.created_from_alert` | 新建 Incident 时 | payload:`{incident_id, alert_name, service, operation, occurrence_count}` |
| `incident.alert_merged` | `touched_firing` 更新既有 Incident 时 | payload 含 `occurrence_count` |
| `incident.alert_resolved` | resolved 路径汇总为 RESOLVED 时 | 不表示恢复,payload 明确 `"recovered": false` |
| `run.auto_started` | `mark_dispatched` 成功后 | payload:`{run_id, trigger_source: "alertmanager"}` |

- 事件写入复用 `event_repo.append_event`;在聚合事务内落库需要 session 版本
  (`append_event_in_session`),避免在已提交事务外再开 Session 造成"事件与聚合不同源";
- `incident_event.event_type` 为 `String(32)`,上表 5 个事件名最长 27 字符,均在列宽内;
- 现有 `_emit_status`/`status_changed` 语义不变,前端 SSE 消费者按新事件名增量处理。

## 十一、并发与重启测试计划

| 场景 | 期望 |
|---|---|
| Dispatcher 在 `capture_run_baselines` 后、`mark_dispatched` 前崩溃 | 同事务回滚;租约过期后重领,**不重复写**基线 |

## 十二、风险点

1. **冻结契约被触碰**(§3.2):`freeze_baselines` 是"创建后写入",与 V2.0-A 的
   "创建事务内冻结"表述不同。已用三重闸门(status/无 checkpoint/字段为空)约束,
   但需在审查中确认可接受(见 D1-a)。
2. **Prometheus 历史窗口依赖观测栈**:本机 fixture 后端无历史数据 → 本机测试必须
   注入假 Prometheus 客户端;真实窗口行为只能在服务开启后做 live 验收。
3. **`SELF_RECOVERED` 新终态**会波及 `TERMINAL_STATUSES`、Replay outcome、前端文案、
   既有测试断言(如 `needs_human/recovered/failed` 枚举处),需全量回归。
4. **Verifier 关闭 fail-open** 可能改变既有 SCN E2E 的恢复判定,必须逐条确认而非放宽阈值。
5. **`resolved_recheck` 增加图节点** → 图拓扑/checkpoint 兼容性:新增节点对**已存在
   checkpoint 的旧 Run** 可能造成恢复路径变化(旧 checkpoint 里没有该节点)。需验证
   LangGraph 在同一 thread 上新增节点后的 resume 行为;必要时用"仅在 resolved 时才
   走新节点、否则直连 diagnose"的条件边降低影响,并补一条"旧 checkpoint + 新图"回归测试。
6. **同事务关闭 Incident** 会扩大 `update_run_status` 的事务范围(多一次
   `incident_alert`/`alert_instance` 查询),需确认不影响既有终态写入性能与锁顺序
   (避免与聚合事务形成死锁;建议统一加锁顺序:incident → alert_instance → agent_run)。
7. 事件写入改为 session 版可能影响既有 `append_event` 调用点,需保持行为不变。

## 十三、需裁决的决策

- **D1-a 基线采集时机**:推荐"Dispatcher 启动前一次性冻结"(§3.2,唯一能同时满足
  "webhook 快速返回"与"E3 有真实基线"的方案)。替代方案:保持 `baseline=None`,
  接受自动 Run 只能到 `needs_human`(等于放弃 V2.1-C 完成标准)。
- **D1-b 手动创建 Incident 是否也切历史窗口**:推荐本切片只改自动路径,手动路径保留
  实时快照但**改名并标注**;若要求手动路径也走历史窗口,需要人工提供 `startsAt` 语义。
- **D2 历史窗口参数**:`[startsAt-10m, startsAt-1m]`、最小样本数 30、健康阈值 100ms
  (与 demo 告警规则同源)。这些值是否需要先做校准脚本(方案完成标准提到阈值校准)?
- **D3 `SELF_RECOVERED` 的判定阈值**:无健康基线时用显式 SLO(100ms)还是直接
  `INCONCLUSIVE` 转人工?推荐前者(与 §六 一致),但会引入一个"人为阈值"。
- **D4 `alert.received` 语义**:事件表以 incident 为键,只能在聚合后发。是否接受该偏离,
  或改为新增"未关联告警"审计表(超出本切片范围)?
- **D5 前端范围**:本切片是否包含 `web/` 展示(告警生命周期徽标、基线质量、新 SSE 事件)?
  推荐后端 API 先暴露(坐席可见),前端展示单独一小切片,避免与后端回归耦合。
- **D6 提交粒度**:建议拆 3 个提交 —— ①`012` + 基线冻结与历史窗口;②resolved 复核 +
  Preflight + Verifier;③episode 关闭 + SSE + API 暴露。每个提交各自跑全量测试。
