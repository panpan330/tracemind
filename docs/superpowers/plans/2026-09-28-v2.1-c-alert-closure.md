# TraceMind V2.1-C "告警闭环" 实施计划(v2,按 10 条裁决修订,待复核)

> **v2 修订(裁决逐条吸收,v1 相应条目作废):**
> ① 基线采集**不置于数据库长事务内**:外部采集(Prometheus HTTP + 业务库 digest 读)
>    先于事务完成;随后用**短 CAS 事务**校验租约 owner、`status='queued'`、
>    `dispatch_status='CLAIMED'`、无 checkpoint(未启动)、`baseline_capture_status IS NULL`,
>    单次封存基线并 `mark_dispatched`,同事务提交;
> ② 明确自动 Run 的**两阶段冻结**契约;区分**有效空 digest 快照 `{}`** 与**未采集 `None`**;
> ③ 手动 Incident 本版不改历史窗口,但**当前故障值不得再充当健康基线**(实时值改存独立
>    标注列;健康基线权威来源改为 `baseline_metrics_json` 且仅 `quality='OK'` 时可用);
> ④ 历史窗口参数**配置化**;真实验收前执行**健康/故障分布校准**;
> ⑤ 自愈与恢复验证使用**与告警相同的 HTTP P95 指标、服务和操作**,取**恢复信号后的
>    新鲜样本**;直接 SQL 耗时只能作**独立佐证**,不得作为恢复信号;
> ⑥ Preflight 同时覆盖 **CREATE_INVENTORY_INDEX 与 TERMINATE_BLOCKING_SESSION 两条写路径**;
>    新 FIRING 仅触发重新取证,**不得**以 `last_seen_at` 晚于 Proposal 作为拒绝依据;
> ⑦ episode 关闭检查**所有非终态 Run**(不只 `active_run_key`);锁顺序与网关一致;
> ⑧ 补充 **SCN-002 告警→自动调查映射**分析与 E2E 验收;
> ⑨ Incident SSE **只在关联后发**,原始告警由 `alert_event` 留痕;前端至少识别
>    `self_recovered` 终态;
> ⑩ 本文件即修订后的**决策表 + 状态/事务边界 + 测试清单**,复核通过后再实施。

**Goal:** 告警自动创建的 Incident 能完成一次**可信**的完整调查——基线来自告警 `startsAt`
之前的历史窗口(不是故障态实时值),`resolved` 到达时做复核而不是直接宣告恢复,调查终止
且全部告警非 FIRING、无任何非终态 Run 后才关闭 episode。

## 三、两阶段冻结契约(自动 Run)

### 3.1 阶段定义

| 阶段 | 时机 | 写入内容 | 幂等闸门 |
|---|---|---|---|
| **阶段 1**(既有,V2.0-A) | Run 创建事务 | RunContextSnapshot(service/operation/severity/调查窗口/checkpoint/四类版本)+ 冻结版本列;`incident_digest_baseline=None`(未采集)、`baseline_capture_status=None` | 事务内一次 |
| **阶段 2**(本切片新增) | Dispatcher 领取后、图启动前 | digest 快照 + 健康窗口指标 + 质量 → `agent_run.incident_digest_baseline`、`baseline_capture_status`、快照 `baseline_ref/healthy_baseline_ref/baseline_quality/baseline_window`;`incident.baseline_window_*/baseline_metrics_json/baseline_quality/auto_run_started_at`;`mark_dispatched` | 短 CAS(见 T2) |

- 阶段 2 之后(`status` 离开 `queued`、或 `baseline_capture_status` 非空)任何路径
  (恢复/续跑/进程重启)只读不写;`run_context.freeze_baselines` 的 CAS 前置条件即
  "阶段 2 未发生",重复调用抛 `RunContextInvalid`。
- 恢复窗口:`CLAIMED` 后进程崩溃 → 租约过期重领 → 阶段 2 重做(此前未封存,无重复)。
- `CAPTURE_FAILED`(Prometheus 不可达等瞬态)仅在仍未启动时可重试;
  `OK` / `INSUFFICIENT` 为**终值,不重采**(单次封存)。

### 3.2 digest 快照 `{}` 与 `None` 的语义区分

| 值 | 含义 | `_load_run_baseline` 行为 | E3 语义 |
|---|---|---|---|
| `None` | 未采集(阶段 2 未发生/失败) | 抛 `BASELINE_INSUFFICIENT`(不变) | `passed=None` → unknown,不确认根因(V2.1-B 语义) |
| `{}` | **有效空快照**:采集时确无目标 digest 行 | 返回 `{}`(**需放宽现判定**:仅 `None`/非 dict 才抛) | 增量按"当前值即增量"计算:`slow_query_service.list_expensive_digests` 现行 `baseline.get(digest, {0,0,0})` 已天然支持;当前也无行 → delta 空 → 触发既有重采(受决策预算上界) |
| `{digest: {...}}` | 正常快照 | 返回 | 现行增量语义不变 |

配套:`baseline_capture_status` 使该区分在 Run 级显式可审计
(`OK`+`{}` = 已封存且确无目标行;`None` = 未采集;`INSUFFICIENT` = 健康窗口不合格)。

### 3.3 历史健康窗口(配置化)

```python
# settings(V2.1-C 新增;全部可由环境变量覆盖)
baseline_window_before_start_s: int = 600    # startsAt-10m
baseline_window_end_offset_s: int = 60       # startsAt-1m(避开告警前沿)
baseline_min_samples: int = 30               # 最小样本数
baseline_max_p95_ms: int = 100               # 健康阈值(与告警规则阈值同源)
slo_p95_ms: int = 100                        # 显式 SLO(无合格基线时使用)
```

- 不合格(样本不足 / 窗口 p95 已超阈值=故障早于告警)→ `baseline_quality='BASELINE_INSUFFICIENT'`,
  `baseline_metrics_json` **不写健康值**(不伪造);E1/Verifier 走显式 SLO(§七)。
- Prometheus 客户端新增 `query_at(template_id, labels, window_seconds, at_time)`(instant
  显式 `time`)与 `sample_count(...)`(`count_over_time` 固定模板);仍只执行
  `promql_templates.TEMPLATES` 注册模板,**不接受 LLM 生成 PromQL**。

## 四、状态与事务边界(核心)

> 原则:外部 I/O(Prometheus / 业务库只读 / Java)一律不处于任何数据库事务内;
> 每个数据库事务都是短事务;锁顺序与网关聚合事务一致
> (`alert_instance → incident_alert → incident → agent_run`)。

| # | 事务 | 触发 | 内容 | 边界与锁 | 失败语义 |
|---|---|---|---|---|---|
| **T1** | webhook 聚合事务 | POST webhook(既有 + 增量) | alert_event 插入 → alert_instance FOR UPDATE → incident_alert FOR UPDATE → incident FOR UPDATE → occurrence/alert_status → agent_run 插入 → **关闭条件只读判定**(§九)→ **SSE session 内追加**(§十一) | 锁顺序与 011 相同;新增部分全部只读或同 Session 写入 | 整事务回滚 + 有上限重试(既有) |
| **T2** | 基线封存 + 调度 CAS | Dispatcher `claim_queued_run` 成功后 | **事务外采集**:Prometheus 历史窗口(HTTP)+ digest 快照(业务库只读连接,用后即关)→ **短事务**:① `SELECT incident ... FOR UPDATE`(与网关同序,先 incident 后 agent_run)→ ② `UPDATE agent_run SET 基线列, baseline_capture_status, ... WHERE id=:id AND status='queued' AND dispatch_status='CLAIMED' AND lease_owner=:owner AND lease_until>=:now AND baseline_capture_status IS NULL`(单语句原子校验+封存)→ ③ `UPDATE incident SET baseline_*, auto_run_started_at` → ④ `mark_dispatched`(status→investigating)→ 提交 → `start_investigation` | 锁顺序 incident → agent_run(与 T1 一致);HTTP/业务库调用**在事务开启前完成** | CAS 影响行数=0(租约被回收/已封存/已启动)→ **不启动图**,消耗本轮容量,Run 留待重领;采集异常 → `CAPTURE_FAILED`(可重试)或不启动 |
| **T3** | Run 终态 | 图结束/`_terminate_*`/恢复拒绝(既有) | agent_run 终态 + 清 `active_run_key`/租约 | 单行 | 既有 |
| **T4** | episode 关闭 | T3 **提交后**独立短事务;或 T1 内只读判定命中时随 T1 写入 | `incident_alert FOR UPDATE → incident FOR UPDATE`(与 T1 同序)→ 条件判定(§九)→ `lifecycle_status='CLOSED', open_group_key=NULL, closed_at=now` | 不取 agent_run 行锁(只读计数)→ 与 T2/T3 无环 | 条件不满足 → 跳过(幂等);已在 CLOSED → 跳过 |
| **T5** | resolved 复核 | 图节点(每轮证据评估后) | 动态读 `incident.alert_status`(短读,事务外);HTTP 指标调用事务外;决策写 Replay | 无长事务 | 指标不可用/过期 → 不宣告恢复,继续调查 |
| **T6** | Preflight | 两条写路径执行前 | 只读复核(§八):索引存在性 / EXPLAIN / 新鲜 HTTP P95 / 锁等待关系 / 审批状态;结果写 Replay+审计 | 事务外只读 | 拒绝 → **零写操作** + `needs_human` + 原因码 |
| **T7** | 写执行 | 审批通过后 | 既有:`fix_service.execute_fix`(幂等键/no_op)与 `session_terminator.execute`(8 项重查);**前置加 T6** | 既有 | 既有 |

**边界说明(需复核确认):**

1. T2 是"两段式"的代价:采集完成到 CAS 提交之间,租约可能恰好过期 → CAS 失败、
   本次采集作废(无副作用,只是重做)。这是把外部 I/O 移出事务的正确代价。
2. T4 与 T3 分离后的窗口:Run 已终态但 episode 尚未关闭 → 此间同组新 FIRING 仍**合并进
   既有 episode**(`open_group_key` 未清),不会拆成两个 Incident;关闭总是晚于终态,
   方向单向,无竞态危害。
3. T1 内的关闭判定是只读的(命中条件时随 T1 写入,锁已持有,不新增锁);
   T3 后的关闭是独立短事务。两条路径共用同一条件函数,行为一致。
4. `recover_pending_runs` 恢复的 Run **不经过 T2**(已启动过):基线以阶段 2 已封存值为准;
   若崩溃发生在 T2 之前(从未启动),重启后由 Dispatcher 重新领取并走 T2。

## 七、自愈与恢复验证:统一 HTTP P95 信号(裁决⑤)

- **恢复信号 = 与告警相同的指标**:ORDER_CREATE 的 HTTP P95
  (`HTTP_SERVER_P95_V1` 固定模板 + `operation_registry` 真实 URI 正则),服务/操作取
  RunContextSnapshot 冻结的 `service_ref` / `affected_operation_ref`(自动 Run 即
  服务端映射的告警标签);`_probe_p95_ms` 直连 SQL 耗时**降级为独立佐证**,
  不参与 recovered 判定。
- **新鲜样本**:恢复判定所用样本的 `latestSampleAt` 必须晚于恢复信号时刻
  (resolved 到达 / 写动作完成)且在 `metrics_max_age_seconds` 内;过期 → 重采
  (有界重试)→ 仍过期 → `INCONCLUSIVE`。
- 判定(与 §七 v1 一致,补充指标来源约束):

| 情形 | 判定 |
|---|---|
| `baseline_quality='OK'` | `p95_after <= baseline.p95 * 1.2`;`result` 记录来源=baseline |
| 无合格基线 | 显式 SLO:`p95_after <= settings.slo_p95_ms`;记录来源=SLO |
| SLO 也无法判定(p95 缺失/样本过期) | `status='INCONCLUSIVE'` |

- `RecoveryCheck.status` 为 `String(16)`,`INCONCLUSIVE`(12)可容纳;
  `nodes.verify_recovery_node` 增分支:`INCONCLUSIVE → needs_human + recovery_inconclusive`
  (与 `recovery_failed` 区分,既不宣告恢复也不宣告失败)。
- `_p95_recovered` 的 **fail-open 删除**(现状 `baseline is None → return True`)。

## 八、Preflight:双写路径、前置条件判据(裁决⑥)

新增 `app/services/preflight.py`,由两条写路径在执行前调用:

```python
def preflight(incident_id, proposal, approval, agent_run_id) -> PreflightResult:
    """确定性复核;拒绝时零写操作。"""
```

| 检查 | CREATE_INVENTORY_INDEX | TERMINATE_BLOCKING_SESSION | 不通过 |
|---|---|---|---|
| 审批已批准/未过期(既有) | ✓ | ✓(terminator 已有) | 拒绝 |
| 前置条件仍成立:重新 EXPLAIN(仍 `access_type=ALL`)+ 索引仍不存在 | ✓ | — | 拒绝 `PREFLIGHT_PRECONDITION_CHANGED` |
| 锁等待关系仍成立(blocker 仍持锁) | — | ✓(terminator 8 项重查保留) | 拒绝 `evidence_stale` 等(既有) |
| 当前故障未自愈:新鲜 HTTP P95 仍高于阈值(基线或 SLO) | ✓ | ✓ | 拒绝 `PREFLIGHT_ALREADY_RECOVERED` |
| `incident.alert_status` 与 `lifecycle_status` 当前值复核 | ✓ | ✓ | 记录进 Replay 决策(**不单独作为拒绝依据**,见下) |

- **删除 v1 的 `last_seen_at`/`closed_at` 时间戳判据**:新 FIRING 仅意味着重新取证,
  不是 Proposal 失效的证据;是否可执行只看**当前前置条件**(上表)。
  `alert_status='RESOLVED'` 且指标已恢复由"未自愈检查"覆盖;
  `alert_status='FIRING'`(新 episode 告警)不阻止执行,但 Preflight 结果与实测值
  全量写 Replay(`PREFLIGHT_PASSED` / `PREFLIGHT_REJECTED`),供坐席审计。
- KILL 路径的接入点:`session_terminator.execute` 在既有 8 项重查**之前**插入
  共享 Preflight(审批/未自愈检查),保持其 `execution_result` 三结果语义不变;
  索引路径接入点:`fix_service.execute_fix` 在 `FIX_ACTIONS` 校验之后、DDL 之前。

## 九、episode 关闭(裁决⑦)

```python
def maybe_close_incident(session, incident_id) -> bool:
    """同一事务内全部满足才关闭:
    ① incident.alert_status == 'RESOLVED';
    ② 关联 AlertInstance 全部非 FIRING(复用 _firing_instances_remaining == 0);
    ③ 不存在非终态 Run:NOT EXISTS (agent_run WHERE incident_id=:i
       AND status NOT IN run_repo.TERMINAL_STATUSES);   ← 按 status 判定,不只 active_run_key
    ④ lifecycle_status 仍为 'OPEN'。
    → lifecycle_status='CLOSED', open_group_key=NULL, closed_at=now;返回是否关闭。
    """
```

- ③ 同时校验 `active_run_key IS NULL` 与 `status` 终态(双保险,以 status 为权威);
- 调用点与锁顺序见 §四 T1/T4;`TERMINAL_STATUSES` 含本切片新增的 `SELF_RECOVERED`;
- 不变量:resolved 且 Run 未终态 → 不清 `open_group_key`、不关 lifecycle;
  关闭后再次 FIRING → `open_group_key` 为 NULL → 新 episode(新 Incident + 新 queued Run);
- 死锁核对:T4 只按 `incident_alert → incident` 加锁,agent_run 只读;
  T2 按 `incident → agent_run`;T1 按 `alert_instance → incident_alert → incident → agent_run`

## 十、SCN-002 告警→自动调查映射与 E2E(裁决⑧,D7)

**映射分析(已核对代码):**

- 告警面统一为 `OrderOperationP95High → order-service / ORDER_CREATE`(锁阻塞使
  ORDER_CREATE 变慢,与缺索引共享同一表面症状);锁场景无独立可观测指标
  (栈内无 MySQL exporter),新增专项告警规则需要新 instrumentation → 推荐 V2.4 再做。
- 根因区分完全由证据路由完成:自动 Run 的 `affected_operation_ref=ORDER_CREATE` 下,
  E3(有真实基线后)在锁场景大概率 `delta>0 → True`,但 **E4=False(EXPLAIN 走索引)→
  scn001 refuted**;E5=False → `x_index_normal` 排他成立;L1/L2(锁证据,参数为固定
  占位引用,不依赖 operation_ref)→ scn002 confirmed → `decide_root_cause` 裁决锁根因。
- **映射核对发现的风险点**:`capabilities/mysql_missing_index/capability.py::evaluate_digests`
  的"E3=False(锁场景确定性否定)"分支以 `affected_operation_ref == 'INVENTORY_RESERVATION'`
  为键 —— 自动 Incident 映射为 ORDER_CREATE 时该分支不触发。v2 **不改语义**,用特征测试
  钉死自动映射下的 E3 行为(delta>0→True 被 E4 否决;delta=0→重采受预算上界),确保
  自动路径不依赖 `INVENTORY_RESERVATION` 值。

**E2E 验收(服务开启后执行,记入验收报告):**

- 注入 SCN-002 锁故障 + 负载 → Alertmanager 触发同一规则 → 自动 Incident + queued Run
  → T2 采集基线 → 自动调查确认 `LONG_RUNNING_TRANSACTION_BLOCKING_INVENTORY_RESERVATION`
  → 审批 → **Preflight 通过** → KILL(8 项重查)→ 恢复验证(HTTP P95 新鲜样本 + 锁证据,
  SQL 探针为佐证)→ episode 关闭;
- 对照:SCN-001 自动路径 E2E(索引创建)同轮执行,两条链路共用同一告警规则。

## 十五、风险点

1. **图拓扑变更**(`resolved_recheck` 插入 `collect_evidence → diagnose` 之间)对**已存在
   checkpoint 的旧 Run** 的 resume 兼容性:需补"旧 checkpoint + 新图"回归测试;必要时改为
   仅 resolved 时才进入新节点的条件边。
2. **T2 两段式的窗口**:采集与封存之间租约过期 → 本次采集作废重来(无副作用,但
   突发告警时可能重复查询 Prometheus,需对采集结果做 run 级去重日志以便观察频率)。
3. **手动路径切换 SLO** 改变既有 SCN-001/002 手动 E2E 的判定路径(基线→SLO),预期结果
   不变但必须逐条回归,不得放宽阈值。
4. **`SELF_RECOVERED` 新终态**波及 `TERMINAL_STATUSES`、Replay outcome、SSE、前端。
5. **锁顺序变更风险**:T2/T4 是新增事务,已按网关顺序设计(§九),但需以真实并发测试
   (测试 27)验证无死锁。
6. **Prometheus 历史窗口依赖观测栈**:本机 fixture 无历史数据,测试注入假客户端;
   真实窗口行为与校准只能在服务开启后验证。
7. **`healthy_metrics_baseline` 读取切换**:存量行含故障态值,切换后不再被读取;
   若有测试/脚本仍依赖该列,需一并适配。
