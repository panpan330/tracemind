# TraceMind V2.1-B "聚合与调度" 实施计划(v3,含 5 项确定性修正)

> v3 修正(复核通过方向后的确定性修正,已批准直接 TDD):
> ① resolved 汇总按实例全集判定(任一 FIRING → Incident 仍 FIRING);
> ② CLAIMED 过期租约可重领,DISPATCHED 永不重领,CLAIMED→DISPATCHED CAS 校验 owner+租约;
> ③ max_concurrent_runs 按 runner 存活任务真实计容量(非"单轮领一个");
> ④ open_group_key 冲突/死锁 → 整事务回滚 + 有上限整事务重试(统一 ORM Session,不混用 conn);
> ⑤ group_key 用 canonical_json 结构化哈希(无分隔符拼接);dispatch_status 库默认 DISPATCHED
>    (存量/手动=DISPATCHED,仅 alertmanager queued 显式 READY);审批绑定损坏时保持
>    fail closed 与活动锁,不猜测清键。

> **For agentic workers:** 本切片按方案 §V2.1 条目 4-8 实施;V2.1-C(resolved 复核闭环、
> 历史健康基线采集、SELF_RECOVERED、告警闭环 E2E)不在本轮。TDD:先写聚合/Dispatcher
> 特征测试(红),再实现。v1 计划的 9 条复核意见已全部吸收,差异见各节标注。

**Goal:** 告警经 Webhook 快速持久化(事件+投影+聚合+queued Run 同一事务)后,由数据库租约
Dispatcher 异步领取并启动调查;崩溃后租约回收、准确 Run 恢复。

**Architecture:** Webhook(同步、快速)= 单事务完成 事件→投影→聚合→关联→queued Run;
Dispatcher(后台 loop)= 租约领取 → CAS DISPATCHED → 快照驱动的 start_investigation。
单实例声明不变;SQLite checkpointer 下 max_concurrent_runs 强制为 1。

## Global Constraints

- Webhook 不同步运行 Agent、不同步采集基线;Agent 启动只在 Dispatcher;
- `open_group_key` 活动期唯一(NULL 可重复);`active_run_key` 活动期唯一;
- 三状态分离:incident.alert_status(FIRING/RESOLVED)/ incident.lifecycle_status
  (OPEN/CLOSED,C 才关闭)/ agent_run.status(含新增 queued);
- 每 Incident 只允许一次告警触发的自动 Run(仅 Incident 创建时);终态后重复 firing
  只累计 occurrence,不自动重跑;
- capabilities 包禁止导入 agent.policies/facts(既有架构测试继续有效);
- 未推送链:无(V2.1-A 四提交已在 origin/main=595414e;本版新提交待验收后推)。

## 四、不完整标签语义(复核意见 6,唯一语义)

## 五、聚合原子事务(复核意见 1)

**同一事务 = 事件 + 投影 + 聚合 + 关联 + queued Run**。`run_repo` 拆出 session-aware 内部方法
`_insert_run_in_session(session, incident_row, *, baseline, trigger_source, status,
active_run_key)`,不自行提交;公开 `create_run`(manual 路径)包装独立事务。聚合事务伪代码:

```python
# 统一 ORM Session.begin()(事件/投影/Incident/关联/AgentRun 共用同一 Session,不混用 conn)
MAX_TX_RETRIES = 3
for attempt in range(1, MAX_TX_RETRIES + 1):
    session = Session(get_control_engine())
    try:
        with session.begin():
            event_id = insert_alert_event(session, ...)   # 唯一键冲突 → duplicate delivery
            action = upsert_instance(session, ...)        # FOR UPDATE(同实例行锁)
            if action == "archived_late_firing":
                pass  # commit 仅事件 → matrix(archived),无聚合无 occurrence
            resolved = resolve_alert(labels)              # 服务端映射;None → 仅归档+ignored
            linked_incident_id = None
            if action in {"created_firing", "touched_firing"}:
                linked = (session.query(Incident).join(IncidentAlert)
                          .filter(IncidentAlert.alert_instance_key == ik)
                          .with_for_update().first())
                if linked:
                    linked_incident_id = linked.id
                    linked.occurrence_count += 1
                    linked.last_seen_at = ra
                    linked.alert_status = "FIRING"
                else:
                    group_key = group_key_hash({source, alertname, env, service, operation})
                    incident = (session.query(Incident)
                                .filter(Incident.open_group_key == group_key)
                                .with_for_update().first())
                    if incident is None:
                        incident = Incident(..., open_group_key=group_key,
                                            occurrence_count=1, lifecycle_status="OPEN",
                                            alert_status="FIRING", status="created")
                        session.add(incident); session.flush()   # 拿 id
                        is_new_incident = True
                    else:
                        incident.occurrence_count += 1
                        incident.last_seen_at = ra
                        incident.alert_status = "FIRING"
                    session.add(IncidentAlert(incident_id=incident.id,
                                              alert_instance_key=ik))  # 权威关联(实例唯一)
            if action in {"advanced_resolved", "touched_resolved"}:
                if linked_incident_id is None:
                    linked_incident_id = (经 incident_alert 查询;resolved 分支独立查权威关联)
                if linked_incident_id:
                    firing_left = EXISTS(  # 任一关联实例仍 FIRING → Incident 保持 FIRING
                        incident_alert ia JOIN alert_instance ai
                        ON ia.alert_instance_key = ai.alert_instance_key
                        WHERE ia.incident_id = :lid AND ai.current_status = 'FIRING')
                    # 全部非 FIRING → alert_status='RESOLVED'
                    # (不关 lifecycle、不清 open_group_key、无 SELF_RECOVERED)
                    if not firing_left:
                        linked.alert_status = "RESOLVED"
            if is_new_incident and resolved is not None:
                _insert_run_in_session(session, incident, baseline=None,
                    trigger_source="alertmanager", status="queued",
                    active_run_key=f"incident:{incident.id}", dispatch_status="READY")
        # COMMIT
        return counters_delta
    except (IntegrityError, OperationalError) as exc:
        session.close()   # 失败 Session 不复用(禁止在失败 Session 中继续查询)
        if not _is_group_conflict_or_deadlock(exc) or attempt == MAX_TX_RETRIES:
            raise ToolBusinessError("AGGREGATION_RETRY_EXHAUSTED", retryable=True)
        continue  # 整事务重试:从 AlertEvent 重新开始;胜者已提交,
                  # 重试方重读胜出 Incident 完成关联与 occurrence(事件 hash 不同不冲突)
```

- 不同 fingerprint、同 group 不受 fingerprint advisory lock 串行,唯一裁决 = open_group_key
  唯一键;冲突/死锁 → 整事务回滚 + 有上限重试(3 次),耗尽 → retryable 错误。```

- 并发同 group:open_group_key 唯一键 + FOR UPDATE 串行;冲突插入 → 捕获后重读走更新路径
  (响应无 500)。并发不同 group:互不阻塞。
- **故障注入测试**:分别于 投影 / Incident 插入 / incident_alert / Run 插入 抛异常 →
  事务回滚(事件也无)→ 重试收敛,无孤儿(无 Incident-无事件、无 Instance-无事件、
  无 queued-无 Incident)。

## 六、Run/Dispatch 状态转换表(复核意见 3、8)

**AgentRun.status(运行语义)**;终态集合 `TERMINAL = {recovered, failed, needs_human,
rejected, cancelled}`(集中定义于 run_repo):

| from \ to | queued | investigating | awaiting_approval | executing | verifying | 终态 |
|---|---|---|---|---|---|---|
| created(manual) | —(manual 直接 investigating) | ✓ | ✓ | ✓ | ✓ | ✓ |
| queued(自动) | — | ✓(DISPATCHED CAS) | ✗ | ✗ | ✗ | ✓(回收/取消) |
| investigating | ✗ | —(循环) | ✓ | ✓ | ✓ | ✓ |
| awaiting_approval | ✗ | ✓(resume) | — | ✓ | ✓ | ✓ |
| 终态 | ✗ | ✗ | ✗ | ✗ | ✗ | — |

- update_run_status:终态即 `active_run_key=NULL, lease_owner=NULL, lease_until=NULL`
  (所有终止路径含审批绑定损坏→needs_human、cancelled;取消入口=api 手动取消,C 阶段暴露)。
- dispatch_status 状态机(仅 queued 运行):`READY → CLAIMED → DISPATCHED`:

```
CLAIMED:   UPDATE dispatch_status='CLAIMED', lease_owner=:o, lease_until=now+lease,
           dispatch_attempts=dispatch_attempts+1
           WHERE id=:id AND status='queued'
             AND ( (dispatch_status='READY')
                OR (dispatch_status='CLAIMED' AND lease_until < :now) )  -- 过期 CLAIMED 可重领
             AND dispatch_status != 'DISPATCHED'                       -- 永不重领
                                                                        -- rowcount=1 才算领取
DISPATCHED: UPDATE dispatch_status='DISPATCHED', status='investigating'
           WHERE id=:id AND status='queued' AND dispatch_status='CLAIMED'
             AND lease_owner=:o AND lease_until >= :now   -- 校验 owner + 租约未过期
           → rowcount=1 才 start_investigation;租约过期后原 owner 不得启动图
```

- `max_concurrent_runs`:唯一来源为 `runner.max_concurrent_runs()`(按**实际
  checkpointer 类型**判定,当前恒为单实例 SqliteSaver → **强制为 1**,与
  checkpoint_path 的扩展名无关);Dispatcher 每轮领取前计算剩余容量 =
  `runner.max_concurrent_runs()` − runner 存活任务数
  (`runner.pending_task_count()`,含 recover_pending_runs 恢复的 investigating
  任务)。第一个图阻塞时,任意多次 tick 第二个 Run 保持 queued;终态释放容量后
  才能领取(复核修正 ③)。未来换共享 checkpointer 才在该单点放开。

## 七、事件 × occurrence/alert_status 处理矩阵(复核意见 2)

| 动作(action) | alert_event | occurrence | incident 聚合/更新 | queued Run |
|---|---|---|---|---|
| duplicates(同 delivery_hash) | 不落 | — | — | — |
| created_firing(labels 完整) | 落 | +1(新建=1) | 新建 OPEN 或更新 last_seen/alert_status | 仅新建 Incident 时建 1 个 |
| created_firing(labels 不完整) | 落 | — | 无(ignored reason=incomplete_labels) | 无 |
| touched_firing(完整) | 落 | +1 | 更新 last_seen/alert_status=FIRING | 无(活动 Run 已存在) |
| touched_firing(不完整) | 落 | — | 无 | 无 |
| advanced_resolved | 落 | — | 关联 Incident:任一关联实例仍 FIRING → 保持 FIRING;全部非 FIRING → RESOLVED | 无 |
| touched_resolved | 落 | — | 同上 | 无 |
| created_resolved(resolved-only) | 落 | — | 无(只归档,方案 V2.1-4) | 无 |
| archived_late_firing | 落 | — | 无 | 无 |

occurrence 定义 = **非重复 FIRING 通知数**(created_firing 与 touched_firing);
duplicate 与 archived_late_firing 不计;resolved 类不计。聚合触发按上表动作判定,
不以 "projected" 粗粒度判断。

## 八、Dispatcher 与崩溃窗口/恢复路径(复核意见 3)

Dispatcher:`app/services/dispatcher.py`,`dispatch_loop` 每 `dispatch_interval_seconds`:
`claim_queued_run(owner)` CAS 领取 ≤ max_concurrent_runs(SQLite 下强制 1)→
CAS DISPATCHED+investigating → `runner.start_investigation(run.id)`(快照驱动)。
lifespan 启动(`dispatch_enabled`)与关闭(cancel + await,复核意见 9);
测试环境默认关闭,Dispatcher 测试显式开启。

| 崩溃窗口 | 落点状态 | 恢复路径 |
|---|---|---|
| queued 插入后、领取前 | queued/READY,无租约 | Dispatcher 正常领取 |
| CLAIMED 后、图启动前(进程死) | queued/CLAIMED,租约未到期 | 不领取;租约过期后重领(attempts+1) |
| DISPATCHED/status=investigating 后、首个 checkpoint 前 | investigating,无 checkpoint | 宿主重启 → recover_pending_runs 以冻结快照重建初始状态(现有 V2.0-A 路径),active_run_key 未清,不新建 Run |
| investigating 且有 checkpoint | investigating | 重启 → 从原 checkpoint 恢复(现有) |
| 图终态后、清 active_run_key 前 | 状态已终态/键残留 | update_run_status 终态统一清键;若进程死于清理前,重启后该 Run 若仍 investigating/awaiting_approval 由恢复路径走到终态后清键 |
| 审批挂起中重启 | awaiting_approval | 审批决策 resume(现有);Dispatcher 不触碰 |

- Dispatcher 不重复启动:dispatch_status CAS(READY→CLAIMED 单胜)+ status 过滤
  (只领 queued);investigating/awaiting_approval 不在领取集。
- 租约回收:领取谓词含 `lease_until < now`(含 CLAIMED 残留)。

## 九、基线语义(复核意见 4)

- alertmanager 触发的 queued Run:`baseline=None`(不采集、不把累计值当基线);
- `_load_run_baseline`:Run 存在但 baseline 为 None → 返回 `BASELINE_INSUFFICIENT` 标记
  (不是空基线);`list_expensive_digests` 据此返回 insufficient;
- `_evaluate_digests`:insufficient → E3 证据 `passed=None`(unknown),**禁止确认根因**
  (F_TARGET_QUERY_EXPENSIVE 缺失 → scn001 必 unknown);scn002 不依赖 E3,不受影响;
- capabilities `extract_facts`:`passed=None` 的证据键不输出 Fact(unknown 语义),
  既有 bool 行为不变;
- 手动 Run(api/runs.py)保留"开始调查时采集新鲜基线"(基线有效);
- V2.1-C:独立一次写入的历史基线快照(012),不覆写 RunContextSnapshot。

21. 并发不同 fingerprint 同 group:真实唯一键冲突 → 整事务重试后 Event/Instance/
    Incident/关联/Run 全部收敛;
22. 两个 queued Run:第一个图阻塞(测试注入慢图)时多次 tick → 第二个保持 queued;
    第一个终态释放容量后第二个才被领取(真实容量计算);
23. group_key:canonical_json 结构化哈希(键序不敏感、分列保存);dispatch_status
    库默认 DISPATCHED(存量/手动 Run 不入调度);
24. 伪造 Content-Length/无 Content-Length 分块超限 → 413(V2.1-A closure 既有,回归)。

## 十二、风险点

1. 聚合事务变长(含 Run 快照构建):demo 量级毫秒级,advisory lock + 唯一键兜底;测试 1 覆盖;
2. queued Run 无基线 → scn001 走 unknown→预算耗尽 needs_human:语义诚实但演示观感变化,
   V2.1-C 历史基线修复(交接文档记录);
3. 状态转换集中化只覆盖 dispatch 生命周期与终态,不全量重构既有图内状态流(避免回归);
4. Dispatcher 与 approval_scanner/runner 并发:queued 仅 Dispatcher 领取;investigating
   恢复仍归 recover_pending_runs;active_run_key 唯一兜底;
5. test_alert_gateway 既有断言适配(FIRING 建 Incident)需逐条核对语义。
